# Mathematical Foundations of queryproof Falsification Probes

queryproof treats SQL generated by language models as untrusted input. Standard linters and database query planners check syntax and schema presence, but they cannot detect mathematical bias or logical distortions. queryproof enforces five deterministic falsification probes before execution.

---

## 1. Join Fan-Out and Cardinality Multiplier Guard (Probe 1)

### 1.1 The Mathematical Problem
In relational data warehouses, table relationships often have one-to-many ($1:N$) cardinality. For instance, one customer row in `customers` ($R_1$) relates to $k$ rows in `orders` ($R_2$).

When an analytical query joins $R_1$ with $R_2$ and computes an aggregate function $\sum(m)$ or $\text{AVG}(m)$ over a column $m \in R_1$, naive SQL evaluates the aggregate over the multiplied join output rather than the original parent relation:

$$\text{Observed Aggregate} = \sum_{i=1}^{|R_1|} \left( k_i \cdot m_i \right)$$

where $k_i$ is the number of child records associated with parent record $i$.

If the true intended business metric is $\sum_{i=1}^{|R_1|} m_i$, the naive query multiplies the reported figure by the average fan-out factor:

$$\Phi_{\text{join}}(R_1, R_2) = \frac{|\sigma_{\text{join}}(R_1 \bowtie_k R_2)|}{|R_1|}$$

In enterprise datasets with 20 orders per customer on average, naive join queries report 2,000% of actual customer MRR.

### 1.2 Detection Rule
Probe 1 inspects:
1. Every `JOIN` clause in the AST.
2. The primary and foreign key definitions between participating tables in the catalog.
3. Every aggregate function call (`SUM`, `AVG`, `COUNT`).

If $\Phi_{\text{join}} > 1.0$ and an aggregate references a column from the parent table without grouping or pre-aggregation, Probe 1 raises a `CRITICAL` severity violation.

### 1.3 Deterministic AST Remediation
queryproof extracts the child relation into an isolated Common Table Expression (CTE) grouped by the join key:

```sql
-- Before (Falsified)
SELECT c.id, SUM(c.mrr) AS total_mrr, COUNT(o.id) AS order_cnt
FROM customers AS c
INNER JOIN orders AS o ON c.id = o.customer_id
GROUP BY c.id;

-- After (Certified Rewrite)
WITH orders_agg AS (
  SELECT customer_id, COUNT(id) AS order_cnt
  FROM orders
  GROUP BY customer_id
)
SELECT c.id, SUM(c.mrr) AS total_mrr, o.order_cnt
FROM customers AS c
INNER JOIN orders_agg AS o ON c.id = o.customer_id
GROUP BY c.id;
```

## 2. Nullability Masking and Division Guard (Probe 2)

### 2.1 Unprotected Division by Zero
In SQL, dividing by zero or dividing nullable columns causes runtime query failures or unexpected NULL propagation:

$$\frac{A}{B} \quad \text{where } B \in \{0, \text{NULL}\}$$

Probe 2 checks every division operator `/` in the AST. If the denominator is not protected by `NULLIF(..., 0)`, it wraps the expression:

$$\text{COALESCE}\left(\frac{A}{\text{NULLIF}(B, 0)}, 0\right)$$

### 2.2 Silent Upward Mean Distortion
ANSI SQL specifies that aggregation function `AVG(col)` skips NULL values in both the numerator and the denominator:

$$\text{AVG}_{\text{SQL}}(S) = \frac{\sum_{s \in S, s \neq \text{NULL}} s}{|\{s \in S \mid s \neq \text{NULL}\}|}$$

If column `discount_pct` represents promotional discounts where a NULL value represents zero discount, dropping NULL rows distorts the true average:

$$\text{True Mean} = \frac{\sum_{s \in S} \text{COALESCE}(s, 0)}{|S|}$$

For example, given rows `[10%, NULL, NULL, 0%]`, `AVG()` returns `5.0%`. The true average discount across all four transactions is `2.5%`.

Probe 2 cross-references column nullability against the catalog. If a nullable measure is averaged, it wraps the column with `COALESCE(col, 0)`.

### 2.3 Three-Valued Logic in Subqueries
When using `col NOT IN (SELECT other_col FROM ...)`, if any row returned by the subquery evaluates to NULL, the comparison `col != NULL` evaluates to `UNKNOWN`. In ANSI SQL, `NOT (UNKNOWN)` remains `UNKNOWN`, causing the entire `WHERE` clause to filter out 100% of candidate rows.

Probe 2 flags `NOT IN` clauses targeting subqueries with nullable projection columns.

## 3. Semantic Metric Invariant Guard (Probe 3)

### 3.1 Divergence Formula
Enterprises define key metrics (such as Annual Recurring Revenue, Net Churn Rate, or Gross Margin) in an authoritative file (`metrics.yaml`). When text-to-SQL models generate ad-hoc formulas, they frequently introduce discrepancies.

Probe 3 calculates normalized formula divergence $\Delta_{\text{metric}}$ between candidate expression $T_{\text{sql}}$ and certified definition $T_{\text{cert}}$:

$$\Delta_{\text{metric}} = 1 - \frac{|T_{\text{cert}} \cap T_{\text{sql}}|}{|T_{\text{cert}} \cup T_{\text{sql}}|}$$

If $\Delta_{\text{metric}} > 0.05$, Probe 3 reports an uncertified formula violation.

### 3.2 Dimension and Filter Invariants
A metric definition may require specific filters (for example, `deleted_at IS NULL` or `status = 'active'`) and permit only certified dimensions (such as `region` or `tier`). Probe 3 verifies that candidate queries include all mandatory filters and do not group across unapproved attributes.

## 4. Governance and Isolation Guard (Probe 4)

Enterprise tables often enforce soft-delete patterns (`deleted_at IS NULL`) and multi-tenant scoping (`tenant_id = :tenant_id`). When an LLM omits these conditions, queries leak soft-deleted records or cross-tenant data.

Probe 4 verifies that any query referencing a table with configured tenancy or soft-delete columns includes the necessary filters in its `WHERE` clause.

---

## 5. Partition Pruning and Budget Guard (Probe 5)

Analytical warehouses (such as BigQuery and Snowflake) charge for queries based on data scanned. On petabyte tables partitioned by date (e.g. `event_date`), omitting a partition filter triggers a full table scan.

Probe 5 checks whether partitioned tables have corresponding filters in the query. It also flags unbounded `SELECT` statements that lack both `GROUP BY` and `LIMIT` clauses.
